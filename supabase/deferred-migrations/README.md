# 보류된 마이그레이션

여기 있는 `.sql` 파일은 **`supabase/migrations/`의 정상 순서에 들어 있지 않다.** 일부러다.

## 왜 따로 두는가

`supabase/migrations/`는 "받아서 순서대로 다 적용하면 되는 것"이다. 그런데 이 파일들은
**아직 적용하면 안 된다** — 서버 스키마보다 클라이언트가 먼저 따라와야 하기 때문이다.

`capacitor.config.ts`는 `webDir: 'dist'`이고 `server.url`이 없다. JS 번들이 APK 안에 구워져
있다는 뜻이고, 학생이 새 APK를 **설치하기 전까지 구버전 앱은 계속 구버전 코드로 동작한다.**
서버만 먼저 바꾸면 그 학생들의 쓰기가 조용히 실패한다 — 앱은 에러 하나 안 띄우고, 매니저는
0분을 본다.

같은 폴더에 두면 `supabase db push`나 "밀린 마이그레이션 순서대로 적용"이 이 파일까지
함께 삼킨다. 그래서 폴더를 나눈다. 여기 있는 파일은 **한 번에 하나씩, 손으로, 아래 전제
조건을 확인한 뒤에만** 적용한다.

## 적용하는 법

전제 조건을 확인한 뒤 파일 내용을 Supabase SQL 에디터에 직접 붙여 실행하고, 그 다음
`supabase/migrations/`로 옮겨 다음 번호를 붙인다(그래야 새로 만드는 환경에서는 순서대로
적용된다).

## 목록

### `0021_drop_study_session_deviated.sql`

- **하는 일**: `sb_study_sessions.deviated` 컬럼 삭제. 허용 목록 전환으로 이탈 감지가
  사라진 뒤 이 컬럼에 `true`를 쓰는 코드가 없다.
- **전제 조건**: **모든 학생이 투트랙 전환(당시 `tutor-student-two-track` 브랜치, 현
  `main`) 이후로 빌드된 APK를 설치했을 것.**
- **어기면**: 구버전 앱은 학습 세션을 만들 때(insert)와 끝낼 때(update) 모두 이 컬럼에
  쓴다. 컬럼이 없으면 두 쿼리가 다 실패해서 **그 학생들의 학습 시간이 아예 기록되지
  않는다.** 매니저 화면에는 0분이 뜬다. 학생도 매니저도 무엇이 잘못됐는지 알 방법이 없다.
- **확인하는 법**: 학생 기기의 앱 버전을 확인하거나, 최근 학습 세션이 정상적으로 쌓이는
  학생 목록과 실제 학생 목록이 일치하는지 본다.
