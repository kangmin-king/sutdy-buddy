## 답변의 기준이 되는 정의 두 개

양식을 잘못 채우는 대부분의 원인이 이 둘입니다. 먼저 짚습니다.

**1. "수집(Collected)"은 기기 밖으로 나가는 것만입니다.**
플레이는 데이터가 **기기에서 전송될 때** 수집으로 봅니다. 기기 안에서만 쓰고 서버로 보내지
않는 것은 수집으로 신고하지 않습니다. 이 앱에는 그런 처리가 두 개 있습니다(아래 3장).

**2. "공유(Shared)"는 제3자에게 이전하는 것입니다.**
개발자를 대신해 처리하는 **서비스 제공자**로의 이전은 공유가 아닙니다. Supabase, Vercel,
Amplitude, Google(FCM)은 모두 서비스 제공자입니다. 따라서 이 앱은 **모든 항목에서 "공유 안
함"** 으로 답합니다.

## 2장. 수집한다고 신고할 항목

모두 **공유 안 함**, **일시적 처리 아님**입니다. 목적 칸만 항목별로 다릅니다.

### 개인 정보 (Personal info)

| 데이터 유형 | 필수/선택 | 목적 | 무엇인지 |
| --- | --- | --- | --- |
| **이메일 주소** | 필수 | 앱 기능, 계정 관리 | 로그인 식별자. Supabase Auth |
| **사용자 ID** | 필수 | 앱 기능, 계정 관리, 분석 | 계정 UUID. Amplitude에도 같은 값이 전송됨 |

이름·전화번호·주소·생년월일은 수집하지 않습니다 — 스키마에 필드 자체가 없습니다.

### 앱 활동 (App activity)

| 데이터 유형 | 필수/선택 | 목적 | 무엇인지 |
| --- | --- | --- | --- |
| **앱 상호작용** | 필수 ⚠️ | 분석 | 화면 조회, 세션 시작·종료, 유입 경로, 기능 사용 이벤트, **세션 리플레이** |
| **기타 사용자 생성 콘텐츠** | 필수 | 앱 기능 | 숙제, 계획(플래너), 학습 기록, 학습 목표, 사용 교재, 학교 시간표, 모의고사 기록과 시험 범위, 과외 일정 |
| **기타 작업** | 필수 | 앱 기능, 분석 | 학습 세션 시작·종료 시각과 공부한 시간, 공부 중 허용앱 사용 시간 구간 |

> ⚠️ **"앱 상호작용"을 필수로 답해야 하는 건 지금 분석을 끌 수 없기 때문입니다.**
> 동의 여부로 켜고 끌 수 있게 만들면 **선택**으로 답할 수 있고 심사에도 유리합니다. 5장 참고.

### 기기 또는 기타 ID (Device or other IDs)

| 데이터 유형 | 필수/선택 | 목적 | 무엇인지 |
| --- | --- | --- | --- |
| **기기 또는 기타 ID** | 선택 | 앱 기능, 분석 | FCM 푸시 토큰(알림 권한을 허용한 경우에만), Amplitude 기기 ID |

알림 권한을 거부하면 FCM 토큰이 만들어지지 않으므로 **선택**이 맞습니다.

## 3장. 수집하지 않는다고 답할 항목 — 특히 헷갈리는 것

### 설치된 앱 목록 / 화면에 떠 있는 앱 → **수집 안 함**

"딴짓 멈춰"는 설치된 앱 목록을 읽어 허용앱 선택 화면을 그리고, 접근성 서비스로 지금 화면에
올라온 앱을 판단합니다. **둘 다 기기 밖으로 나가지 않습니다.**

- 서버로 보내는 코드가 없습니다(`ForegroundAppAccessibilityService.kt`에 네트워크 호출 없음)
- 서버에 저장되는 것은 **시간 구간뿐**이고 어떤 앱이었는지는 저장하지 않습니다
  (`sb_allowed_app_intervals`에 컬럼 자체가 없음)
- 전체 앱 목록 조회 권한(`QUERY_ALL_PACKAGES`)은 쓰지 않고, 매니페스트 `<queries>`로 필요한
  범위만 조회합니다

따라서 **App activity › 설치된 앱**은 "수집 안 함"입니다.

> 다만 이건 데이터 보안 양식의 문제가 아니라 **민감 권한 공개**의 문제로 따로 남습니다.
> 접근성 서비스와 "다른 앱 위에 표시" 권한은 앱 내에서 목적을 명확히 알리는 화면
> (prominent disclosure)이 필요하고, 접근성 서비스 사용 자체가 심사에서 가장 큰 쟁점입니다.

### 앱 안의 캘린더 → **캘린더 아님**

플레이의 **캘린더 이벤트**는 **기기 캘린더**를 뜻합니다. 이 앱은 자체 캘린더 화면을 쓰고 기기
캘린더에 접근하지 않습니다. 따라서 캘린더는 "수집 안 함"이고, 그 내용은 2장의
**기타 사용자 생성 콘텐츠**에 들어갑니다.

### 나머지 전부 수집 안 함

| 카테고리 | 이유 |
| --- | --- |
| 위치 (대략·정확) | 위치 권한도 플러그인도 없음 |
| 금융 정보 | 결제 기능·SDK 자체가 없음 |
| **건강 및 피트니스** | 아래 5장 ⚠️ 참고 |
| 메시지 | 메시지 기능 없음 |
| 사진 및 동영상 / 오디오 / 파일 및 문서 | 카메라·마이크·저장소 접근 없음 |
| 연락처 | 연락처 권한 없음 |
| 웹 탐색 기록 | 수집하지 않음 |
| **앱 정보 및 성능** (비정상 종료 로그, 진단) | 크래시 리포팅 SDK가 없음. Crashlytics·Sentry 모두 미사용. Firebase는 메시징(FCM)만 씀 |

## 5장. 제출 전에 정리해야 하는 것 ⚠️

양식을 사실대로 채우면 아래 세 개가 그대로 드러납니다. 양식 문제가 아니라 앱의 문제라
코드나 정책을 손대야 합니다.

### (1) 세션 리플레이 × 아동 대상 선언 — 가장 큰 충돌

`src/lib/analytics.ts`가 `sessionReplay: { sampleRate: 1 }` 로, **전체 세션의 화면 조작을
녹화**합니다. 학년이 `중1`부터라 대상 연령에 아동이 포함되면 플레이의 가족 정책이 적용되고,
아동 데이터 수집은 강하게 제한됩니다. **만 13세 학생의 화면 조작을 100% 녹화하는 것은 그
정책과 정면으로 부딪칩니다.**

선택지: 표본율을 낮춘다 / 성인(관리자) 세션에만 켠다 / 동의 항목으로 분리한다 / 끈다.

### (2) 접근성 서비스

데이터 보안 양식과는 별개지만 같은 제출 흐름에서 걸립니다. 접근성 서비스를 앱 차단에 쓰는
것은 반려 사유가 되는 대표 사례이므로, `UsageStatsManager` 전환 또는 목적 선언 + 데모 영상
준비가 필요합니다.

### (3) `sb_daily_conditions` 테이블을 지우는 편이 안전합니다

`sleep_hours`, `fatigue`, `focus`, `mood` 컬럼을 가진 테이블이 DB에 남아 있습니다. 지금은
**어떤 화면도 읽거나 쓰지 않습니다**(`src/types/db.ts`의 타입 정의에만 존재). 폐기된 "컨디션
입력" 기능의 잔재입니다.

그래서 지금은 "건강 및 피트니스 수집 안 함"이 맞습니다. 하지만 **이 기능을 되살리면 수면
시간과 기분이 건강 정보가 되고, 심사 기준이 크게 올라갑니다.** 되살릴 계획이 없다면
테이블을 드롭해서 신고 대상에서 완전히 지우는 게 깔끔합니다
(`supabase/deferred-migrations/`에 같은 성격의 정리 마이그레이션 선례가 있습니다).

### (4) 안 쓰는 권한 하나

매니페스트에 `FOREGROUND_SERVICE` 권한이 선언돼 있는데 `startForeground` 호출이 코드에
**0건**입니다. 안 쓰는 권한은 심사에서 질문거리가 되고 권한 목록만 늘립니다 — 제거 권장.

## 6장. 판단이 갈릴 수 있는 지점 하나

**연결된 과외쌤·학부모가 학생의 학습 기록을 보는 것을 "공유"로 신고해야 하는가?**

저는 **아니오**로 봤습니다. 플레이의 "공유"는 제3자 **회사·기관**으로의 데이터 이전을 뜻하고,
같은 서비스 안에서 사용자가 수락한 상대에게 보이는 것은 앱의 기능입니다. 사용자 간 공개
기능은 데이터 보안 양식이 아니라 기능 설명과 개인정보처리방침에서 다루는 영역입니다.

다만 이 앱은 그 공개가 **핵심 기능**이므로, 스토어 설명과 방침에 범위를 분명히 적어두는 것이
안전합니다. 방침 4장에 이미 적어뒀습니다.
